## Machine display stream - 2026-11-22

The machine does not send displayed text as ASCII strings. The 6800's PIA activity is captured as ordered `DisplayOperation`/`ScreenCommand` events with coordinates and control bits: text glyphs become dot marks, while `BufferClock` coordinates form vector segments in the emulation renderer. ASCII is used on separate paths such as keyboard input and BASIC file payloads.

The ordered text marks include positions within the character dot grid, but no character identity or stroke/pen-up boundaries. Connecting consecutive marks directly would not reliably recover a stroke font; that requires a character-specific tracing map.

The Extended renderer composes the glow over a separate, unchanged standard WebGPU frame. ## WASM input-performance investigation - 2026-11-18

In headed Chrome 158 at 1280x720 on this host, x100 BASIC prompt/cursor averaged 1182.42% of the 10 ms advance budget with WebGPU (about 118 ms per call; 113 ms average frame) and 491.55% with forced CPU fallback (about 49 ms per call; 49 ms average frame). A single Playwright key at the BASIC prompt showed page-to-key-handler delays of 4.2, 73.2, 203.9, and 338.2 ms at x1/x20/x50/x100 with WebGPU, versus 2.4, 29.6, 76.7, and 151.1 ms with CPU fallback. These are one-event host-specific dispatch samples, not key-to-PIA or BASIC-echo measurements; WebGPU x100 produced no qualifying (>=16 ms) Event Timing entries, while the page-side handler probe still recorded both key events.

The browser calls `emulator.advance()` synchronously from `requestAnimationFrame`. `HostRuntime::sync_display` already applies ordered display operations and submits one GPU batch per machine batch. However, each `TransientCursorMark` appends two segments to WebGPU's transient list; that list persists until the 100 ms display refresh. Every dirty machine batch then serializes/uploads and redraws the entire accumulated transient list. The CPU reference event queue deduplicates cursor marks only within each drained operation batch, so repeats across machine batches can inflate WebGPU work. Additional queue batching alone is unlikely to remove this repeated geometry preparation. Rust-side cursor-mark deduplication is a candidate for a separately authorized follow-up; it is deferred under the current no-Rust-change scope.

## PIA keyboard-handshake proposal

The user-supplied unofficial note proposes waiting for a keyboard PIA read and CA2 transition before loading another key. ### Compatibility boundaries

- `HostRuntime::start()` supplies display readiness when no erase is pending. A reset erase stays pending for the host's 500 ms completion callback; without readiness, the bounded reset run waits at `0xC6B4`.
- Board interrupt routing deliberately uses raw PIA status flags without enable gating, matching the web reference. CPU IRQ masking, NMI priority, held-source suppression, and rearming are tested.
- ROM selectors 2/3 return read-only zero bytes only within `0x8800..0xA7FF`, normalizing the reference's undefined bytes; this is not general JavaScript undefined/NaN or floating-bus parity. Selector 1 maps `0x8800..0x97FF`; selector 4 maps its exact 2 KiB payload at `0x8800..0x8FFF`. Their uncovered tails remain explicit errors, not fallback ROM/zero mappings.
- Pointer presses and intervening releases use the shared 50/30 ms sequenced-key timing, unlike the web's immediate transitions. Rapid taps are queued and source ordering/modifiers preserved. This needs native interaction validation.
- Pausing stops CPU, keyboard callbacks, and display refresh. Each erase request has an independent 500 ms completion retained across pause, runtime restart, and execution errors; the later callback still blanks the screen after an earlier one signaled readiness. Save As dialog time advances only these independent erase callbacks, not interval work. The native shell no longer has a separate Reset-only erase timer.
- Screen-copy buffering retains up to eight ordered event-time snapshots. Excess requests are counted and visibly reported without stopping emulation. Native destination choice and modal pause differ from the web's automatic download.
- GPIB input replacement preserves the existing cursor as in the web source; polling the last byte or explicitly clearing resets it. Empty or exhausted input polls as `0xff` with EOI. RTC command `0x6d` samples host-local time with Jiff, propagating clock or timezone failures; other RTC commands are ignored as in the web reference. The year modulo 100 is not padded. The partial tape stores numbered files at 1 through 254; FIND of ASCII/BINARY selects a byte snapshot, while missing/marker selections retain snapshot and record cursor. SAVE/BSAVE update the store at the preceding FIND number to an ASCII/binary program at EOI, with blank stored description, without replacing the current metadata/contents or snapshot. CLOSE clears those views and selection but retains cursor and pending WRITE clear. Writes lacking their required number, unsupported tape commands, malformed headers, and selections requiring the web's file dialog report errors.
- Tape PRINT (`0x6c` at address 5) replaces current-file bytes when the shared INPUT/PRINT cursor is zero and otherwise appends. It advances the cursor by the entire resulting buffer length, matching the web's unusual arithmetic, and does not refresh the FIND snapshot. INPUT beyond that snapshot leaves shared input unchanged. Missing FIND clears the current-file view while retaining snapshot/cursor; subsequent PRINT can create the numbered file. Checked cursor overflow reports an error without committing changed file bytes. The Rust numbered subset deliberately rejects the web's accidental unnumbered entry.
- Binary WRITE (`0x6f`) commits the single outbound byte on every DAV transfer, regardless of EOI, without advancing the shared cursor. FIND of ASCII/BINARY DATA arms clearing for the next selected WRITE; later bytes append. Preserve the private clear flag across CLOSE and non-data/missing/marker FIND and header writes: the web's public `writeClrFlg` assignments do not reset private `#writeClrFlg`. Clearing precedes the type guard, so an ignored ASCII or LAST WRITE can clear working contents without committing them. NEW PRINT/WRITE converts to ASCII/DATA or BINARY/DATA; LAST rejects both. LOG/TEXT transfers retain usage, while INPUT/READ depend on ASCII/BINARY type and return `0xff` otherwise.
- Binary READ (`0x6e`) sends the entire current binary file only at cursor zero, then sets the web's consumed marker `99`. Further READ calls retain shared input, even for files longer than 99 bytes; FIND of an existing ASCII/BINARY file rewinds. READ sees working contents while OLD sees the FIND snapshot. SAVE may replace the store with ASCII while READ still sees the prior binary working contents until FIND.
- Binary-program command `0x71` selects BSAVE for listener addressing and BOLD for talker addressing. BOLD requires a selected binary program, uses the FIND snapshot, and appends `0xff` plus spaces: 1 through 256 padding bytes, including a full extra block for empty/aligned snapshots. It is repeatable without advancing or resetting READ's cursor; incompatible or missing selections leave shared input unchanged. WRITE preserves existing binary-program usage, and program FIND does not arm data-file clearing. R05 routines use `CALL "BSAVE",5` / `CALL "BOLD",5`, not standalone statement syntax. Synthetic keyboard tests must enter their quotation marks using Shift+2.
- LIST read (`0x73` with talker addressing, BASIC `INPUT@5,19:A$`) returns file number/type/usage/description padded to 7/8/5/16 columns, followed by a space and unpadded decimal current byte size, with no CR/NUL suffix. NEW/LAST are valid without usage. It describes current working metadata, not the canonical store after SAVE or an ignored WRITE clear. Untyped/missing/CLOSE states send `0xff`, even if OLD bytes remain or SAVE created a store record. This peripheral operation is distinct from BASIC's program-listing LIST.
- LIST write (`0x73` with listener addressing, BASIC `PRINT@5,19:H$`) parses the first six bytes for a parseInt-style number, type at byte 7, ASCII/BINARY usage at byte 15, and description from byte 20 to the final space. Strip brackets before truncating/padding the raw one-byte description to 16 bytes; the final size and remaining label letters are ignored. Out-of-range numeric numbers retain the preceding current number. NEW/LAST ignore the supplied usage and retain prior usage. Renumbering saves working contents under the new key without deleting the old entry or changing the FIND/fileNum control used by SAVE/BSAVE; header writes also retain snapshot/cursor/pending WRITE clear. Malformed headers deliberately report a typed Rust error instead of the web's silent rejection. With no usable current/header number, Rust still rejects an unnumbered save.
